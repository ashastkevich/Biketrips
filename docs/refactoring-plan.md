# План очистки и рефакторинга BikeTrips

## Цель

Последовательно убрать legacy-код и технический долг, не нарушая текущие пользовательские сценарии и не смешивая рефакторинг с разработкой новых продуктовых функций.

План основан на аудите статического прототипа, Next.js-приложения, NestJS API, общих пакетов, сборки и поведения интерфейса в браузере.

## Принципы выполнения

- Сначала устранять риски безопасности и целостности данных, затем архитектурный долг и только после этого косметические и производительные улучшения.
- Выполнять этапы небольшими изменениями с отдельными проверками и понятной возможностью отката.
- Не удалять legacy-прототип до подтверждения функционального паритета с Next.js-приложением.
- Не совмещать изменение бизнес-правил с механическим переносом кода между файлами.
- Для каждого этапа запускать `npm run lint`, `npm run typecheck`, `npm test` и релевантные интеграционные или ручные проверки.
- Перед началом каждой задачи проверять рабочее дерево командой `git status`.

## Приоритет P0. Защита данных и разграничение доступа

Эти задачи необходимо завершить до работы с реальными пользователями и публикации приложения.

### 1. Ввести серверную модель ролей и владельцев ресурсов

Работы:

- определить роли `participant`, `organizer` и `admin`;
- связать JWT-пользователя с `User` и `Organizer`;
- получать текущего пользователя из проверенного JWT, а не из тела запроса;
- добавить проверки владельца поездки при редактировании, публикации, отмене и завершении;
- ограничить управление участниками владельцем поездки или администратором;
- запретить изменение `organizerId` через общий DTO обновления поездки.

Результат:

- авторизованный пользователь не может управлять чужой поездкой;
- идентификатор организатора формируется на сервере;
- административные действия явно отделены от действий организатора.

Критерии готовности:

- есть позитивные и негативные тесты для каждой защищённой операции;
- запрос с валидным JWT другого пользователя возвращает `403`;
- запрос без JWT возвращает `401`;
- владелец ресурса успешно выполняет разрешённую операцию.

### 2. Закрыть небезопасные сценарии аутентификации

Работы:

- отключить `dev-login` вне окружений `development` и `test`;
- запретить запуск production API без явно заданного `JWT_SECRET`;
- убрать fallback-секрет из runtime-конфигурации;
- централизовать проверку обязательных переменных окружения;
- определить срок жизни, формат payload и правила обновления токенов;
- проверить настройки cookie: `httpOnly`, `secure`, `sameSite`, срок жизни и удаление при выходе.

Результат:

- production-токен нельзя получить через служебный endpoint;
- приложение не запускается с небезопасным секретом;
- сессия имеет единые и документированные правила.

Критерии готовности:

- тест подтверждает недоступность `dev-login` в production;
- конфигурационный тест подтверждает обязательность production-секретов;
- Telegram login и `/auth/me` проходят интеграционный сценарий.

### 3. Защитить регистрацию участников

Работы:

- перестать принимать доверенный `userId` из публичной формы;
- для авторизованного пользователя брать ID из JWT;
- отдельно спроектировать гостевую регистрацию, если она остаётся требованием MVP;
- добавить защиту от повторной регистрации;
- нормализовать и валидировать Telegram username и телефон;
- определить rate limit для публичной регистрации.

Результат:

- пользователь не может зарегистрировать другого пользователя от его имени;
- гостевой и авторизованный сценарии разделены явно.

Критерии готовности:

- тесты покрывают повторную запись, подмену пользователя и гостевую запись;
- сервер игнорирует или отклоняет переданный клиентом `userId`;
- публичный endpoint имеет ограничение частоты запросов.

### 4. Ограничить доступ к черновикам

Работы:

- публичная лента должна возвращать только опубликованные поездки;
- публичная карточка должна скрывать `draft` и недоступные статусы;
- `includeDrafts` разрешать только авторизованному владельцу или администратору;
- разделить публичные и organizer-запросы на уровне service/repository API;
- проверить отсутствие утечки приватных данных участников в публичных serializers.

Результат:

- черновики и служебные данные невозможно получить через публичные endpoints.

Критерии готовности:

- публичный запрос черновика возвращает `404`;
- владелец видит собственный черновик в кабинете;
- другой организатор не видит чужой черновик.

### 5. Сделать критичные операции атомарными

Работы:

- объединить отмену участия, продвижение очереди и изменение waitlist-записи в транзакцию;
- блокировать поездку или релевантные строки при конкурирующей записи;
- обеспечить уникальность активного участия пользователя в поездке на уровне БД;
- обеспечить уникальность позиции и активной записи листа ожидания;
- определить идемпотентность публикации, отмены, завершения и повторной отправки уведомлений.

Результат:

- параллельные запросы не превышают лимит мест и не продвигают двух участников на одно место.

Критерии готовности:

- интеграционный тест моделирует конкурентную запись на последнее место;
- ограничения БД отражены в миграции;
- повтор операции не создаёт дублирующиеся уведомления или waitlist-записи.

## Приоритет P1. Единый источник данных и доменная модель

### 6. Отделить demo-режим от production data flow

Работы:

- подключить главную страницу к тому же API-слою, который используют остальные страницы;
- убрать прямой импорт `demoTrips` из пользовательских сценариев;
- включать демо-данные только явным feature flag;
- не подменять сетевую ошибку демо-данными без явного уведомления;
- определить отдельные состояния `loading`, `empty`, `error` и `demo`.

Результат:

- все страницы используют единый источник данных;
- ошибка API не выглядит как успешная загрузка реальных поездок.

Критерии готовности:

- при доступном API главная показывает серверные данные;
- при ошибке API показывается контролируемое error-состояние;
- demo-режим включается только заданной конфигурацией.

### 7. Согласовать UI-модель поездки с API-контрактом

Работы:

- определить, поддерживает ли поездка один или несколько типов велосипедов;
- определить, поддерживает ли поездка одно или несколько покрытий;
- убрать магическое значение `500` для обозначения отсутствия лимита;
- представить отсутствие лимита отдельным nullable-полем или явным флагом;
- определить единый формат темпа и средней скорости;
- определить серверную модель обложки поездки;
- убрать клиентские `demo-organizer-1` и `demo-city-moscow`;
- синхронизировать domain types, DTO, entities, serializers и формы.

Результат:

- форма не создаёт данные, которые API вынужден терять или интерпретировать косвенно.

Критерии готовности:

- контракт создания поездки одинаково описан в domain package, OpenAPI и web-форме;
- отсутствуют type assertions, скрывающие несовпадение моделей;
- round-trip `form -> API -> serializer -> form` не теряет значения.

### 8. Централизовать схемы валидации и преобразования

Работы:

- определить единый подход к runtime-валидации общих контрактов;
- вынести правила длины, диапазонов и допустимых значений из компонентов;
- создать явный mapper между form draft и API input;
- валидировать даты, координаты, темп, дистанцию и лимит на сервере;
- добавить проверку связанных полей: `paceMin <= paceMax`, дата в будущем, валидные координаты;
- унифицировать формат ошибок API.

Результат:

- клиент и сервер используют согласованные правила, а преобразования находятся в тестируемых функциях.

Критерии готовности:

- unit-тесты покрывают mapper и связанные правила;
- некорректные данные возвращают структурированную ошибку;
- UI может сопоставить серверную ошибку конкретному полю.

### 9. Завершить или явно ограничить незаконченные интеграции

Работы:

- заменить mock-карту реальным провайдером либо явно обозначить ручной ввод как MVP-решение;
- реализовать загрузку обложки в объектное хранилище либо убрать неработающий upload-контрол;
- определить состояние Telegram-бота, очередей и уведомлений;
- убрать UI-обещания, для которых ещё нет backend-сценария;
- зафиксировать решения в архитектурной документации.

Результат:

- интерфейс не имитирует готовую функциональность, отсутствующую на сервере.

Критерии готовности:

- каждый доступный control имеет законченный серверный сценарий;
- временные решения имеют явный feature flag и срок удаления.

## Приоритет P2. Рефакторинг frontend

### 10. Разделить глобальный CSS

Работы:

- провести инвентаризацию селекторов и удалить неиспользуемые правила;
- выделить design tokens: цвета, типографику, интервалы, радиусы, тени и breakpoints;
- разделить reset/base, layout, UI primitives и feature/page styles;
- объединить повторяющиеся media queries;
- убрать дублирующиеся селекторы и каскадные переопределения;
- выбрать и документировать подход: CSS Modules, feature styles или фактический переход на Tailwind.

Результат:

- изменения отдельной страницы не требуют правки монолитного файла на несколько тысяч строк.

Критерии готовности:

- визуальные regression-проверки пройдены на desktop и mobile;
- нет роста CSS bundle;
- число дублирующихся селекторов и media-блоков сокращено;
- Storybook-компоненты используют те же стили, что и приложение.

### 11. Разделить UI-компоненты по ответственности

Работы:

- разбить `app/ui/components.tsx` на модули `actions`, `forms`, `feedback`, `overlays`, `filters`, `trip` и `participants`;
- убрать дублирование с `app/lib/components.tsx`;
- вынести иконки в отдельный модуль;
- оставить feature-компоненты рядом с соответствующей feature;
- определить правила публичных exports и импортов.

Результат:

- файлы имеют одну понятную ответственность;
- изменение карточки поездки не затрагивает общий файл всех UI-компонентов.

Критерии готовности:

- отсутствуют циклические зависимости;
- Storybook и приложение используют одинаковые exports;
- поведение и публичные props компонентов не изменились без отдельного решения.

### 12. Декомпозировать мастер создания поездки

Работы:

- вынести каждый шаг в отдельный компонент;
- заменить набор связанных `useState` на reducer или специализированный form hook;
- вынести draft persistence и миграцию localStorage в отдельный модуль;
- удалить поддержку draft v1 после согласованного периода миграции;
- вынести выбор обложки, выбор условий и preview;
- сделать навигацию по шагам зависимой от общей схемы валидации;
- корректно очищать черновик после успешной публикации.

Результат:

- мастер можно тестировать по шагам, а изменение одного шага не усложняет весь компонент.

Критерии готовности:

- unit/component tests покрывают восстановление, миграцию, сохранение и удаление черновика;
- тесты покрывают переходы между шагами и ошибки;
- успешная публикация не оставляет устаревший черновик.

### 13. Унифицировать фильтры

Работы:

- создать одну доменную модель фильтров;
- согласовать значения покрытия и типов велосипедов;
- определить, какие фильтры выполняются сервером, а какие клиентом;
- сериализовать фильтры в URL;
- добавить debounce для текстовых и диапазонных фильтров;
- сохранить возможность поделиться отфильтрованной лентой.

Результат:

- главная, API-клиент и backend одинаково интерпретируют фильтры.

Критерии готовности:

- URL восстанавливает состояние фильтров после перезагрузки;
- серверные и клиентские результаты совпадают;
- тесты покрывают комбинации фильтров.

Результат:

Критерии готовности:

Работы:

## Проверки после каждого этапа

Обязательные автоматические проверки:

npm run lint

Обязательные ручные проверки для web-изменений:

- главная страница на desktop и mobile;
- фильтры и пустое состояние;
- открытие и закрытие карточки поездки;

- кабинет организатора;
- навигация только клавиатурой;
- отсутствие overflow, наложений и битых изображений.
